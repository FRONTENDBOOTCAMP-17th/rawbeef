## 2. 잘한 점

### LocalStorage → API 연동 전환

이전에는 LocalStorage에 데이터를 저장했는데, 이번에 **실제 서버 API와 연동**하는 것으로 바꿨어요. 이것은 정말 큰 발전이에요! `fetch()`를 사용해서 GET, POST, PATCH, DELETE 모든 HTTP 메서드를 활용하고, `Authorization: Bearer` 헤더로 인증까지 처리하고 있어요. 실무에서 하는 것과 같은 방식이에요.

```js
// admin_category.js — 깔끔한 API 호출 패턴
const res = await fetch(`${API_BASE}/categories`, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Authorization: `Bearer ${token}`,
  },
  body: JSON.stringify({ title }),
});
```

### 사이드바/헤더 컴포넌트 분리

이전 리뷰에서 "반복되는 사이드바를 분리하면 좋겠다"고 했었는데, `sidebar.js`와 `header.js`로 **멋지게 분리**했어요! 현재 페이지를 자동으로 감지해서 활성 상태를 표시하는 것도 잘 했어요.

```js
// sidebar.js — 현재 페이지 자동 감지
const currentPage = './' + location.pathname.split('/').pop();
const isActive = currentPage === item.href;
```

### JS를 HTML에서 분리

`admin_category.html`, `admin_song.html`, `admin_request.html` 모두 JavaScript를 **별도 .js 파일로 분리**했어요. HTML은 화면 구조만, JS는 동작 로직만 담당하게 되어서 코드를 이해하기 훨씬 쉬워졌어요. 이것이 바로 **"관심사의 분리"** 원칙이에요.

### XSS 방어

사용자 페이지(`user_request.js`, `user_song.js`)에서 `esc()` 함수를 만들어서 사용자 입력값을 HTML에 넣기 전에 **이스케이프 처리**하고 있어요. 보안 의식이 뛰어나요!

```js
// 사용자 입력을 안전하게 화면에 표시
function esc(str) {
  return String(str).replace(/&/g, '&amp;').replace(/</g, '&lt;')...
}
```

### 다크모드 구현

Tailwind CSS의 `dark:` 접두사를 활용해서 다크/라이트 모드를 전환할 수 있게 만들었어요. `style.css`의 `@custom-variant dark` 설정도 잘 되어 있어요.

### 사용자 페이지 완성도

`woohyun/user_song.html`과 `woohyun/user_request.html`은 완성도가 매우 높아요:
- 카테고리 탭 필터링, 검색, 유튜브 아코디언 (user_song)
- 등록 폼 유효성 검사, 페이지네이션, 아코디언 목록, 관리자/일반 사용자 구분 (user_request)
- 반응형 디자인 (`hidden md:block` 등)
- 브레드크럼 네비게이션

### API 기본 URL 중앙 관리

`src/api-config.js`에 API URL을 한 곳에서 관리하는 패턴이 좋아요. 서버 주소가 바뀌면 이 파일만 수정하면 되니까요.

### 에러 처리

API 호출 시 `try-catch`로 에러를 잡고, `res.ok`로 HTTP 상태를 확인하고, 사용자에게 알림을 보여주는 패턴이 일관되게 적용되어 있어요.

## 3. 개선하면 좋을 점

### 3-1. API URL이 두 곳에서 다르게 관리됨 (중요도: 높음)

**현재 상태:**

관리자 페이지는 `api-config.js`의 `API_BASE`를 잘 쓰고 있지만, 사용자 페이지 JS에서는 URL을 직접 적고 있어요.

```js
// src/api-config.js (관리자 쪽에서 사용)
const API_BASE = 'https://api.fullstackfamily.com/api/rawbeef/v1';

// src/user_js/user_song.js (119번째 줄) — URL을 직접 적고 있음!
const res = await fetch('https://api.fullstackfamily.com/api/rawbeef/v1/categories');

// src/user_js/user_request.js (1번째 줄) — 여기도 직접!
const API_BASE = 'https://api.fullstackfamily.com/api/rawbeef/v1/requests';
```

**왜 개선하면 좋을까?**

API 서버 주소가 바뀌면 여러 파일을 찾아다니며 모두 고쳐야 해요. 하나라도 놓치면 그 페이지만 오류가 나요.
이것을 **"결합도(coupling)가 높다"**고 해요. 여러 파일이 같은 정보를 각자 들고 있으면, 하나를 바꿀 때 나머지도 다 바꿔야 하니까요.

**추천:** 사용자 페이지에서도 `api-config.js`를 `<script>` 태그로 먼저 불러오고, `API_BASE`를 활용하세요.

```html
<!-- woohyun/user_song.html, user_request.html -->
<script src="../src/api-config.js"></script>  <!-- 이 줄 추가 -->
<script src="../src/user_js/user_song.js"></script>
```

```js
// src/user_js/user_song.js — API_BASE 활용
const res = await fetch(`${API_BASE}/categories`);
```

```js
// src/user_js/user_request.js — 중복 선언 제거, API_BASE 활용
// const API_BASE = '...' ← 이 줄 삭제
const REQUEST_API = `${API_BASE}/requests`;
```

### 3-2. 테마 저장 방식이 관리자/사용자에서 다름 (중요도: 높음)

**현재 상태:**

```js
// soyu/header.js (36번째 줄) — sessionStorage 사용
sessionStorage.setItem('theme', 'dark');

// src/user_js/theme.js (17번째 줄) — localStorage 사용
if (save) localStorage.setItem('theme', dark ? 'dark' : 'light');
```

**왜 개선하면 좋을까?**

`sessionStorage`는 **브라우저 탭을 닫으면 사라져요.** `localStorage`는 **영구 보관**이에요.
두 곳에서 저장소가 다르면:
- 관리자 페이지에서 다크모드를 켜도, 사용자 페이지에서는 적용이 안 돼요
- 관리자 페이지는 탭을 닫으면 다크모드 설정이 초기화돼요

**추천:** 둘 다 `localStorage`로 통일하세요.

### 3-3. 댓글 없는 신청에서 삭제 버튼 클릭 시 오류 (중요도: 높음)

**현재 상태:**

```js
// soyu/admin_request.js (113~115번째 줄)
deleteBtn.addEventListener('click', async () => {
  if (confirm('이 댓글을 정말 삭제할까요?')) {
    await deleteComment(req.comment.id);  // ← req.comment가 null이면 오류!
```

**왜 개선하면 좋을까?**

신청에 관리자 답변(댓글)이 아직 없을 때 `req.comment`는 `null`이에요. 그런데 삭제 버튼은 항상 표시되기 때문에, 댓글이 없는 신청에서 삭제 버튼을 누르면 `Cannot read properties of null` 오류가 발생해요.

**추천:** 댓글이 있을 때만 삭제 버튼을 보이게 하거나, 클릭 시 확인하세요.

```js
// 방법 1: 댓글 있을 때만 삭제 버튼 추가
if (req.comment) {
  const deleteBtn = document.createElement('button');
  // ... 삭제 버튼 생성
  deleteBtn.addEventListener('click', async () => {
    if (confirm('이 댓글을 정말 삭제할까요?')) {
      await deleteComment(req.comment.id);
      // ...
    }
  });
  btnGroup.appendChild(deleteBtn);
}
```

### 3-5. console.log가 남아 있어요 (중요도: 중간)

**현재 상태:**

```js
// soyu/admin_song.js
console.log(json);                    // 13번째 줄
console.log('songs:', songs);         // 20번째 줄
console.log('저장 데이터:', newSongData); // 106번째 줄
```

### 3-6. `esc()` 함수가 두 파일에 중복 (중요도: 중간)

**현재 상태:**

```js
// src/user_js/user_request.js (7~9번째 줄)
function esc(str) {
  return String(str).replace(/&/g, '&amp;').replace(/</g, '&lt;')...
}

// src/user_js/user_song.js (5~7번째 줄) — 완전히 동일한 코드!
function esc(str) {
  return String(str).replace(/&/g, '&amp;').replace(/</g, '&lt;')...
}
```

**왜 개선하면 좋을까?**

같은 기능의 코드가 두 곳에 있으면, 나중에 하나만 수정하고 다른 쪽을 잊어버릴 수 있어요.
이것을 **"응집도(cohesion)가 낮다"**고 해요. 같은 역할의 코드는 한 곳에 모아두는 것이 좋아요.

**추천:** `src/user_js/utils.js`를 만들어서 공통 함수를 모아두세요.

```js
// src/user_js/utils.js (새 파일)
function esc(str) {
  return String(str).replace(/&/g, '&amp;').replace(/</g, '&lt;')
    .replace(/>/g, '&gt;').replace(/"/g, '&quot;').replace(/'/g, '&#39;');
}
```

```html
<!-- HTML에서 공통 JS를 먼저 로드 -->
<script src="../src/user_js/utils.js"></script>
<script src="../src/user_js/user_song.js"></script>
```

`admin_request.html`과 `admin_song.html`은 다크모드 클래스가 거의 없어요.

```html
<!-- admin_request.html (9번째 줄) — dark: 클래스 없음 -->
<body class="bg-gray-100 font-sans">

<!-- admin_category.html (9번째 줄) — dark: 클래스 있음! -->
<body class="bg-gray-100 dark:bg-gray-950 font-sans">
```

```html
<!-- admin_song.html (14번째 줄) — 검은 테두리만 -->
<div class="flex h-[calc(100vh-57px)] w-full border-4 border-black overflow-hidden">

<!-- admin_category.html (13번째 줄) — 테두리 없이 깔끔 -->
<div class="flex h-[calc(100vh-57px)] w-full overflow-hidden">
```

**왜 개선하면 좋을까?**

같은 프로젝트의 페이지들인데 디자인이 달라요. 사용자가 다크모드를 켰을 때 어떤 페이지는 적용되고 어떤 페이지는 안 되면 일관성이 떨어져요.

**추천:** `admin_category.html`을 기준으로 다른 페이지도 다크모드 스타일을 추가하세요.

---

### 3-8. `<label>` 텍스트가 비어 있음 (중요도: 중간)

**현재 상태:**
```html
<!-- soyu/admin_category.html 33번째 줄 -->
<label for="titleInput" class="block font-black mb-1 text-gray-900 dark:text-white"></label>
```

**왜 개선하면 좋을까?**

`<label>`에 텍스트가 없으면 사용자가 이 입력 칸이 무엇인지 알 수 없어요. `for` 속성으로 연결은 잘 했지만, 보여줄 텍스트가 있어야 의미가 있어요.

**추천:**
```html
<label for="titleInput" class="block font-black mb-1 text-gray-900 dark:text-white">카테고리 이름</label>
```

---

### 3-9. 헤더/푸터 렌더링 방식이 다름 (중요도: 중간)

**현재 상태:**

```js
// soyu/header.js — createElement로 하나하나 만들기
function createHeader() {
  const header = document.createElement('div');
  const logo = document.createElement('span');
  // ...
}

// src/user_js/user_header.js — innerHTML로 한 번에 넣기
document.getElementById('user-header').innerHTML = `
  <header class="sticky top-0 ...">
    <a href="./user_song.html">TJ미디어</a>
    ...
  </header>
`;
```

**왜 개선하면 좋을까?**

같은 역할(헤더 만들기)을 하는데 방식이 다르면, 팀원이 코드를 읽을 때 혼란스러워요.
- `createElement` 방식: 안전하지만 코드가 길어짐
- `innerHTML` 방식: 간결하지만, 동적 데이터를 넣을 때 XSS 위험

**추천:** 한 가지 방식으로 통일하세요. 정적인 HTML은 `innerHTML`이 읽기 쉽고, 사용자 입력이 들어가는 동적 내용은 `createElement`나 `esc()` 함수로 이스케이프하면 좋아요.

### 3-11. 관리자 인증 토큰 만료 처리 없음 (중요도: 낮음)

**현재 상태:**

```js
// soyu/admin_category.js (1~5번째 줄)
const token = localStorage.getItem('adminToken');
if (!token) {
  alert('로그인이 필요합니다.');
  location.href = './admin_open.html';
}
```

토큰이 있는지만 확인하고, **토큰이 만료되었는지**는 확인하지 않아요. API 호출 시 401 응답을 받으면 사용자를 로그인 페이지로 보내야 해요.

**추천:** API 호출 후 401 응답을 처리하는 로직을 추가하세요. (지금 당장 하지 않아도 괜찮지만, 알아두면 좋아요)

```js
// 401 응답이 오면 로그인 페이지로 이동
if (res.status === 401) {
  alert('로그인이 만료되었습니다. 다시 로그인해주세요.');
  localStorage.removeItem('adminToken');
  location.href = './admin_open.html';
  return;
}
```

> 참고: `user_request.js`에서는 이미 401 처리를 잘 하고 있어요! 관리자 쪽에도 같은 패턴을 적용하면 좋겠어요.

이전 리뷰에서 지적한 11개 항목 중 **9개를 해결**했어요! 정말 대단해요! 특히:

- **LocalStorage에서 실제 API 연동으로 전환**한 것은 큰 도약이에요
- **사이드바/헤더를 컴포넌트로 분리**한 것은 "코드 재사용"의 핵심을 정확히 이해한 거예요
- **JS를 HTML에서 분리**하고, **XSS 방어** 함수까지 만든 것은 프로 개발자의 습관이에요
- **사용자 페이지**의 완성도가 특히 높아요. 페이지네이션, 아코디언, 유효성 검사, 관리자/사용자 분기까지!

이번에 지적한 부분들은 대부분 **"일관성"**에 관한 것이에요. 각각의 코드는 잘 동작하지만, 프로젝트 전체를 하나로 보면 방식이 조금씩 다른 부분이 있어요. 팀 프로젝트에서는 이런 일관성이 중요하니까, 하나씩 맞춰나가면 됩니다.
